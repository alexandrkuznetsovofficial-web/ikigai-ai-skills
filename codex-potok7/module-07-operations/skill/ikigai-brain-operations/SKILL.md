# Эксплуатация второго мозга · черновик без прогона

## 🔧 АВТОУСТАНОВКА

Только явный запрос ученика в его отдельной папке разрешает установку. Подготовка, чтение, сборка и редактирование пакета не разрешают устанавливать его в систему автора. START.md содержит все файлы навыка. Сохрани их в `.agents/skills/ikigai-brain-operations/` средствами Codex; не перезаписывай существующие версии. При отличиях покажи узкий план обновления. Не меняй глобальные инструкции Codex.

Прочитай только рабочую карту SYSTEM.md, фокус, handoff и паспорт предыдущего модуля, если сервер уже есть. Создай `.ikigai/module07.json`: module=ikigai-brain-operations, version=0.1.0, status=draft_unrun, phase=prepared, checks=not_run. Запиши ссылку на `memory/operations.md` в свою строку SYSTEM.md, не меняя чужие статусы. Подготовленная инструкция не равна настроенному расписанию.

## 1. Составь карту сохранности

Объясни разницу между синхронизацией (обмен изменениями), снимком (версия данных на момент времени) и восстановлением (возврат выбранной версии). Прочитай [runbook](references/operations-runbook.md). Узнай, что важно не потерять, где лежат файлы, есть ли системный backup компьютера, нужен ли серверный inbox и какой объём данных. Не сканируй все личные каталоги, секреты и конфиги аккаунтов.

Составь паспорт по assets/operations-passport.md. Назови владельца основной копии и места резервных копий. Отдельно отметь голос, картинки, видео и вложения: наш текстовый snapshot их не включает. Для них выбирается системное резервирование или отдельный согласованный метод. Облачный backup и оплата не подключаются по умолчанию.

## 2. Подготовь первый снимок

`scripts/snapshots.py` — локальный текстовый архив с manifest и SHA-256, dry-run по умолчанию, без удаления старых версий. Поддерживаются Python 3.9+ и обычные локальные пути; при отсутствии Python не устанавливай его без объяснения, выбери доступный системный backup и запиши ограничение. Перед `--apply` согласуй место хранения ВНЕ папки мозга. Сначала план, затем явный запрос создать снимок. Папка на том же диске спасает от ошибки редактирования, но не от поломки/потери диска.

Секреты не добавляй в такой архив. Архив не зашифрован. Фильтры путей не доказывают, что человек никогда не записал пароль в MD; при сомнении вынеси секрет в правильное хранилище и отзови раскрытое значение, не печатай его. Права каталога backup должны ограничивать доступ владельцем.

## 3. Настрой самостоятельное восстановление

Покажи ученику путь архива, дату и список версий без раскрытия содержимого. Восстановление скриптом всегда идёт в новую отсутствующую staging-папку, никогда поверх живого мозга. Сначала план, после отдельного выбора — распаковка с проверкой manifest и контрольных сумм. Сравни выбранные файлы с текущими. Живую замену выполняй только по конкретному запросу ученика, предварительно сохранив текущую версию и остановив связанные записи/обмен. Файлы других задач не меняй.

Если ученик просит пока только собрать материалы, не исполняй даже dry-run: оставь checks=not_run. В этой поставке ни одно восстановление не пройдено.

## 4. Выбери ручной режим или расписание

Базовый режим: «сделай снимок перед большой правкой» и «покажи последние снимки». Если человек выбирает расписание, используй OS-specific шаблоны из assets/ и [расписания](references/schedules.md). Заполни абсолютные пути, часовой пояс и выбранную частоту; не включай готовые PLACEHOLDER. На Mac — LaunchAgent, Windows — Task Scheduler с StartWhenAvailable, Linux — user systemd timer с Persistent. Не копируй cron с чужого сервера на ноутбук. Автоматическое удаление старых снимков отсутствует; срок хранения и очистка — отдельное решение ученика.

## 5. Обслуживай, не раздувая контекст

Ручной еженедельный обзор: открытые задачи, обещания, ссылки индекса, фокус до 20 строк, размер постоянных инструкций. Не загружай всю память. Завершённое архивируй по смыслу с сохранением ссылок. Не удаляй историю обещаний. Повторная ошибка → узкое правило и обновление проверки перед действием. Внутренние рассуждения модели не сохраняй; достаточно решения и кратких оснований.

## 6. Обновления и сервер

Прочитай [обновления и инциденты](references/updates-incidents.md). До обновления сохрани текущие файлы/версию навыка, составь diff и план отката. Старую службу останавливай только если доказано, что она принадлежит этому ученику и паку. После реального обновления проверяй необходимые сценарии; если проверки отложены, статус `updated_unverified`, а не успех.

Для сервера модуль 6 использует отдельный state/inbox. Режим `inbox` того же скрипта архивирует только выбранный каталог входящих, не auth, token и SQLite. Входящие сначала импортируются в staging, затем сверяются по update_id. Данные авторизации восстанавливаются через официальный вход; их не класть в общий архив и не пересылать в чат.

## 7. Сохрани итог

Заполни memory/operations.md фактическими данными, укажи: что покрыто, что исключено, где копии, когда было восстановление, расписание и его статус. Обнови SYSTEM.md, MEMORY.md и handoff. Финальный отчёт разделяет «материалы подготовлены», «снимок создан», «восстановление проверено» и «расписание реально сработало». Без наблюдаемого действия оставляй not_run.
