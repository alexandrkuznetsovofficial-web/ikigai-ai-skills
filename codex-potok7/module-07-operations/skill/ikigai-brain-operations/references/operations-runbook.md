# Резервирование и восстановление без перезаписи живой памяти

Статус: исходники составлены без запуска. Команды — действия агента после явного запроса ученика. Участнику не требуется терминал. Выберите собственную папку мозга и отдельное место backup; никакие пути автора не используются.

## Текстовый снимок

1. Проверить текущий путь проекта, отсутствие активной массовой записи/импорта. Уточнить, какая копия главная. Перед согласованным массовым обновлением приостановить только свою автоматическую запись.
2. Выбрать каталог backup вне рабочей папки. Сначала локально, с ограниченными правами. Нужна защита от потери устройства — отдельно выбрать внешний диск/системный backup. Хранилище на одном диске не решает потерю диска.
3. Технический план агента: `python3 snapshots.py snapshot --source <папка-мозга> --dest <отдельная-папка-backup>`. Без --apply скрипт ничего не создаёт. Если ученик попросил лишь подготовить пак, команда не выполняется.
4. По выбранному действию создать снимок тем же вызовом с --apply. Архив получает уникальное имя UTC+random; содержимое текущей папки не меняется. Записать в паспорт только дату, имя, количество и размер, а не содержимое памяти.
5. В архив входят текстовые файлы AGENTS.md, SYSTEM.md, TEAM.md, memory/ и .agents/skills/. Лимит одного файла 20 МБ, суммарно 100 МБ. Форматы: MD, TXT, JSON, Python, TOML, YAML, SH, PS1, service/timer/plist. Служебные секретные категории, .env, .codex, .claude, .git, node_modules, backups исключены; симлинки отвергаются. Медиа, базы и произвольные бинарные вложения НЕ включаются. Отсутствие файла из архива нужно учитывать, а не обещать «всё сохранено».
6. Архив ZIP не зашифрован. SHA-256 подтверждает соответствие содержимого manifest, но не доказывает, кто создал архив. Для надёжности от потери и подмены нужна отдельная копия в выбранном защищённом месте. Никаких автоматических публикаций GitHub.

## Восстановление

1. Ученик выбирает архив и конкретную причину. Сохранить состояние текущей памяти отдельно; не нажимать «восстановить всё» без состава.
2. План: `python3 snapshots.py restore --archive <архив.zip> --staging <новая-отсутствующая-папка>`. Скрипт сверяет пути, состав и контрольные суммы; символические ссылки, выходы за каталог, дубликаты имён и превышение бюджета отвергаются.
3. По запросу ученика — тот же вызов с --apply. Данные распаковываются только в новую staging-папку. Не использовать её внутри действующей памяти или как автоматически синхронизируемый каталог.
4. Сравнить выбранный файл с текущим, объяснить, какие сведения потеряются при замене. Дать выбрать отдельный раздел или файл. Замена действующего файла — отдельное точное действие после сохранения его текущей версии. Скрипт сам этого не делает.
5. Обновить индекс/фокус по факту восстановления, не выдумывать прежние задачи. Если восстановлен старый профиль, подтвердить его актуальность человеком.
6. Только после фактического сравнения/использования отметить restore_checked. Факт распаковки без просмотра не является проверкой полезного восстановления.

## Входящие сервера

`python3 snapshots.py inbox --source <state/inbox> --dest <отдельная-папка-backup>` показывает план. --apply создаёт архив текстовых заметок. Указывать именно inbox, не весь state, HOME или CODEX_HOME. Токен бота, auth.json, очередь SQLite и журнал systemd в архив не входят. Импорт на компьютер — по контракту модуля 6 с проверкой update_id и конфликтов. Уже обработанные входящие не удалять до отдельного решения о сроке хранения.

## При отсутствии Python

Выберите системное резервирование через интерфейс ОС: Time Machine на Mac, доступные средства резервирования Windows, согласованный backup Linux. Зафиксируйте фактическое покрытие и исключения. Не утверждайте, что обычная облачная синхронизация даёт историю восстановления или что папка с копией автоматически зашифрована.
