# 05 · Безопасник

## Модуль безопасности кита «Переезд мозга на сервер»

> Ты только что перевёз свой второй мозг на сервер. Это хорошее, взрослое решение — теперь мозг живёт отдельно от ноутбука, работает по ночам и не пропадёт, если с ноутбуком что-то случится.
>
> Но у сервера есть одна особенность: он смотрит в интернет **всё время**. И туда каждую минуту стучатся не люди, а роботы — автоматические сканеры, которые ищут плохо закрытые двери. Это не про тебя лично, это фоновый шум сети. Наша задача в этом модуле — спокойно, по шагам, закрыть двери, которые робот умеет открывать.
>
> Ничего страшного не произойдёт, если пройти чек-лист. И почти всё, что мы сделаем — **обратимо**. Где необратимо (например, выключить вход по паролю) — мы сначала кладём запасной ключ и только потом закрываем дверь. Ты не останешься снаружи.

Тон этого модуля: не «тебя взломают», а «давай сделаем надёжно, чтобы можно было спать спокойно». Готов? Пошли.

---

## Как читать этот модуль

- Ты не пишешь команды руками. Ты **даёшь агенту в VS Code точные текст-промпты** (они выделены рамкой) — агент сам смотрит, находит проблему и **предлагает** фикс.
- Всё опасное агент делает **только с твоего подтверждения**. Ты в любой момент говоришь «стоп».
- После каждого шага есть строчка **✅ Безопасно, если…** — это твой критерий приёмки. Пока не выполнено — шаг не закрыт.

Плейсхолдеры, которые встретятся ниже (подставь свои):
- `<ИМЯ_ПРОЕКТА>` — короткое имя твоего мозга/бота (напр. папка проекта).
- `<ПОЛЬЗОВАТЕЛЬ>` — твой логин на сервере (не root).
- `<SSH_ПОРТ>` — номер порта для входа на сервер (по умолчанию 22, но мы сменим).
- `<ТВОЙ_ДОМЕН>` — адрес сайта/бота, если есть.
- `<ID_ВЛАДЕЛЬЦА>` — твой Telegram ID (для «белого списка» бота).

## Раздел 1. Где и как хранить пароли и токены безопасно

Токен — это как ключ от квартиры. Пароль от сервера, ключ от Telegram-бота, ключ доступа к модели (подписка) — всё это **секреты**. Если секрет утечёт, чужой человек войдёт как ты.

Три железных правила, которые не нарушаем **никогда**:

1. **Не в чат.** Не вставляй пароль/токен в переписку с ботом, в чат с ассистентом, в мессенджер «самому себе». Чаты сохраняются, пересылаются, попадают в бэкапы.
2. **Не в код.** Не пиши секрет прямо в файле скрипта (`token = "..."`). Код часто уезжает на GitHub — а туда секретам нельзя (см. Раздел 4).
3. **Не в git.** Даже если файл «локальный» — если папка под git, секрет попадёт в историю. А история git помнит всё, даже после удаления.

### Куда же тогда класть? Кросс-ОС хранилища

Правильное место зависит от того, где ты работаешь. Секреты живут в **защищённом хранилище твоей операционной системы**, а программы берут их оттуда.

Важно: у **каждой** ОС есть свой «правильный» способ, и все три равноценны — «по стандарту», не хуже друг друга. Агент на Windows не должен считать нарушением, что там не используется `~/.config` — на Windows эта папка неродная, у неё свой стандарт.

**Windows — `%USERPROFILE%\.secrets\<ИМЯ_ПРОЕКТА>\` или Credential Manager**
- Вариант «файл»: кладём секрет в отдельный файл в личной папке `%USERPROFILE%\.secrets\<ИМЯ_ПРОЕКТА>\` и закрываем доступ так, чтобы читать мог **только владелец** (наследование прав отключается, доступ оставляем себе). Это Windows-аналог `~/.config` с правами 600.
- Вариант «хранилище»: Windows Credential Manager (Диспетчер учётных данных) — Пуск → «Диспетчер учётных данных». Пароли лежат зашифрованными под твоей учёткой Windows; другой пользователь ПК их не увидит.
- Промпт агенту: *«Мне нужно сохранить токен `<ИМЯ_ПРОЕКТА>` так, чтобы он не попал в код и в git. Я на Windows. Предложи стандартный для Windows способ — файл в `%USERPROFILE%\.secrets\<ИМЯ_ПРОЕКТА>\` с доступом только для меня ИЛИ Windows Credential Manager — и покажи, как скрипт будет его оттуда читать. Секрет я введу сам — не проси меня писать его в чат.»*

**macOS — `~/.config/<ИМЯ_ПРОЕКТА>/` (chmod 600) или Keychain**
- Вариант «файл»: `~/.config/<ИМЯ_ПРОЕКТА>/secrets.env` с правами **600** (читать/писать может только владелец).
- Вариант «хранилище»: встроенный Keychain (Связка ключей) — приложение «Связка ключей» или команда `security`.
- Промпт агенту: *«Я на macOS. Помоги сохранить токен `<ИМЯ_ПРОЕКТА>` — либо в файл `~/.config/<ИМЯ_ПРОЕКТА>/` с правами 600, либо в Keychain — и читать его оттуда из скрипта. Сам токен я введу в системном окне/сам впишу, не в чате.»*

**Linux — файл в `~/.config/` с правами 600**
- Кладём секрет в отдельный файл в личной папке настроек: `~/.config/<ИМЯ_ПРОЕКТА>/secrets.env`
- Ставим права **600** — это значит «читать и писать может только владелец, больше никто». Ни другие пользователи, ни веб-сервер.
- Промпт агенту: *«Создай папку `~/.config/<ИМЯ_ПРОЕКТА>/` и файл секретов в ней. Поставь права 600 на файл и 700 на папку. Покажи команду проверки прав. Значение секрета я впишу сам, тебе его не передаю. Убедись, что эта папка НЕ находится внутри git-репозитория.»*

> **Почему 600 — это важно.** На сервере обычно несколько «жильцов»: твой пользователь, веб-сервер, служебные процессы. Права 644 (частая беда) означают «читать может кто угодно на этой машине». Если один процесс взломан — он прочитает твой секрет. Права 600 закрывают эту дверь: секрет видит только его владелец.

✅ **Безопасно, если…** секрет лежит **по стандарту твоей ОС** — Windows: `%USERPROFILE%\.secrets\...` (доступ только владельцу) или Credential Manager; macOS: `~/.config/...` (600) или Keychain; Linux: `~/.config/...` (600); его нет ни в одном файле кода, ни в истории git, ни в переписке; и ты можешь ответить «да» на вопрос «если завтра выложу проект на GitHub — секрет туда не попадёт?».

## Раздел 2. Базовый хардening сервера (чек-лист симптом → фикс)

«Хардening» — по-русски «закаливание». Мы проходим короткий список типовых открытых дверей и закрываем каждую. Для каждой двери: **симптом** (как выглядит проблема), **что говорим агенту**, и **✅ критерий**.

Важно про порядок и обратимость:
- Сначала — **диагностика** (агент смотрит и докладывает). Ничего не меняем.
- Потом — **фиксы**. Безопасные (заголовки, права файлов) — можно сразу.
- **Необратимое** (выключить вход по паролю, перезагрузка, файрвол) — **только с твоего «да»** и **только после того, как проверена запасная дверь по ключу**. Мы не выключаем свет, пока не убедились, что фонарик работает.

### Шаг 0. Общий осмотр (безопасно, ничего не меняет)

> **Промпт агенту:**
> *«Ты — мой офицер безопасности. Проведи осмотр сервера в режиме "только читать, ничего не менять". Проверь и выпиши списком: (1) какие файлы с секретами имеют слишком открытые права (644 вместо 600); (2) включён ли вход по SSH под root и по паролю; (3) на каком порту слушает SSH; (4) есть ли файрвол и fail2ban; (5) давно ли ставились обновления системы; (6) не лежат ли секреты/бэкапы/код в веб-папке; (7) стоят ли security-заголовки у сайта. По каждому пункту дай вердикт 🟢/🟡/🔴 и предложи фикс, но НИЧЕГО пока не меняй — жди моего "да" по каждому пункту.»*

Дальше — по пунктам, которые агент найдёт.

### Дверь 1. Секреты с открытыми правами (world-readable)

- **Симптом:** файлы вроде `.env`, `.session`, файлы окружения имеют права `644` — их может прочитать любой процесс на машине.
- **Фикс:** поставить права `600` (только владелец).
> **Промпт:** *«Покажи все файлы с секретами и их права. Для тех, что доступны на чтение всем, предложи `chmod 600`. Не трогай файлы, которые должны читаться веб-сервером для работы сайта — сначала покажи список и объясни каждый, я подтвержу.»*

✅ **Безопасно, если…** все файлы с секретами показывают права `600`, а сайт/бот после этого продолжают работать.

### Дверь 2. Вход на сервер по паролю под root (самая важная дверь)

- **Симптом:** на сервер можно зайти как `root` по паролю. Роботы это и подбирают день и ночь.
- **Фикс (в правильном, безопасном порядке):**
  1. Создать/использовать обычного пользователя `<ПОЛЬЗОВАТЕЛЬ>` (не root).
  2. **Настроить вход по SSH-ключу** — это твой «фонарик».
  3. **Проверить**, что вход по ключу реально работает — открыть **второе** соединение, не закрывая первое.
  4. Только теперь — **выключить вход по паролю и вход под root**.

> **Промпт (ключ-страховка ПЕРЕД выключением):**
> *«Хочу перейти на вход по SSH-ключу и потом отключить вход по паролю. Действуй строго по шагам и не выключай пароль, пока я не подтвержу, что запасной вход работает. Шаг 1: помоги создать SSH-ключ у меня на компьютере (я на Windows/macOS/Linux — уточни под мою систему). Шаг 2: добавь мой публичный ключ на сервер для пользователя `<ПОЛЬЗОВАТЕЛЬ>`. Шаг 3: дай мне команду проверить вход по ключу во ВТОРОМ окне, НЕ закрывая текущее. Остановись и жди, пока я не скажу "ключ работает". Только после этого переходи к отключению пароля.»*

> **Промпт (выключаем пароль — только после подтверждения):**
> *«Ключ работает, проверил во втором окне. Теперь отключи в настройках SSH вход по паролю и вход под root (`PasswordAuthentication no`, `PermitRootLogin no`). Перед изменением сделай резервную копию конфига с датой в имени. НЕ разрывай мои текущие сессии. После перезапуска SSH дай мне команду проверить, что новый вход по ключу всё ещё работает, а по паролю — уже закрыт. И сразу обнови мой Файл доступа (macOS/Linux: `~/.config/brain/server_access`; Windows: `%USERPROFILE%\.secrets\brain\server_access.txt`): в строке LOGIN= поставь `<ПОЛЬЗОВАТЕЛЬ>`, а в PASSWORD= впиши пометку KEY-ONLY — чтобы любой будущий агент знал: вход теперь только по SSH-ключу, root и пароль больше не работают.»*

✅ **Безопасно, если…** ты **успешно вошёл по ключу во втором окне ДО** отключения пароля; сделан бэкап конфига; после перезапуска ключ работает, а пароль отклоняется; при этом первое окно всё это время оставалось открытым как страховка.

> ⚠️ Золотое правило: **никогда не отключай пароль, пока не проверил ключ в отдельном соединении.** Это единственная в модуле операция, где ошибка = «остался снаружи». Поэтому две проверки и открытое запасное окно.

### Дверь 3. SSH сидит на стандартном порту 22

- **Симптом:** SSH слушает порт `22` — по нему роботы стучатся чаще всего.
- **Фикс:** перевести на нестандартный `<SSH_ПОРТ>`. Это не «настоящая защита», а «убрать вывеску» — фоновый шум падает в разы.
> **Промпт:** *«Помоги сменить порт SSH на `<SSH_ПОРТ>`. Порядок безопасный: сначала РАЗРЕШИ новый порт в файрволе, потом поменяй порт в SSH, потом проверь вход по новому порту во втором окне, и только когда я подтвержу — можно закрывать старый порт 22. Бэкап конфига сделай заранее. В конце допиши в мой локальный Файл доступа строку `PORT=` с новым номером порта — чтобы любой следующий агент подключался по нему, а не по 22.»*

✅ **Безопасно, если…** ты зашёл по `<SSH_ПОРТ>` в отдельном окне до закрытия `22`, и запасное окно оставалось открытым.

### Дверь 4. Файрвол (ufw) — впускать только нужное

- **Симптом:** файрвола нет, открыты все порты.
- **Фикс:** включить ufw. **Критично — порядок:** сначала `allow` для SSH-порта, только потом `enable`. Иначе файрвол закроет твой же вход = локаут.
> **Промпт:** *«Настрой файрвол ufw. ОБЯЗАТЕЛЬНЫЙ порядок, не переставляй: (1) сначала `allow <SSH_ПОРТ>` (и порты сайта 80/443, если есть сайт); (2) покажи мне список правил, я проверю; (3) только после моего "да" делай `enable`. Если перепутать порядок — я потеряю доступ, поэтому строго по шагам.»*

✅ **Безопасно, если…** правило на `<SSH_ПОРТ>` добавлено и **видно в списке ДО** включения файрвола; после `enable` твоё соединение живо.

### Дверь 5. Нет fail2ban (защита от перебора)

- **Симптом:** кто-то может бесконечно подбирать вход, никто его не банит.
- **Фикс:** поставить fail2ban — он временно блокирует IP после нескольких неудачных попыток.
> **Промпт:** *«Установи и включи fail2ban с базовой защитой SSH на порту `<SSH_ПОРТ>`. Покажи, как посмотреть список забаненных, и убедись, что мой IP в белом списке, чтобы я случайно сам себя не забанил.»*

✅ **Безопасно, если…** fail2ban активен, следит за `<SSH_ПОРТ>`, а твой адрес — в исключениях.

### Дверь 6. Устаревшая система и ядро

- **Симптом:** пакеты и ядро давно не обновлялись — в старых версиях бывают известные дыры.
- **Фикс:** включить автоматические обновления безопасности + запланировать перезагрузку (ребут нужен, чтобы обновилось ядро).
> **Промпт:** *«Включи автоматические обновления безопасности. Отдельно: покажи, нужна ли перезагрузка для обновления ядра. Перезагрузку НЕ делай сама — ребут ненадолго уронит сайт/бот. Предложи мне удобное время и выполни только после моего "да". Перед ребутом напомни, что вход по ключу и автозапуск сервисов должны подняться сами.»*

✅ **Безопасно, если…** автообновления включены; ребут выполнен **только** в согласованное с тобой время; после ребута сайт/бот/вход по ключу поднялись сами.

### Дверь 7. Секреты, код и бэкапы лежат в веб-папке

- **Симптом:** файлы `.env`, `.session`, дампы БД, `.git`, `.bak` доступны прямо через браузер по адресу сайта.
- **Фикс:** запретить их отдачу в nginx по расширениям — аккуратно, не сломав нужные файлы.
> **Промпт:** *«Проверь, не отдаёт ли веб-сервер по адресу `<ТВОЙ_ДОМЕН>` служебные файлы: `.env`, `.session`, `.bak`, `.sql`, `.git`, дампы, логи. Если да — добавь в nginx правило `deny` для этих расширений и папок. ВАЖНО: сначала покажи, какие адреса станут закрыты, чтобы я убедился, что не ломаем реально нужные страницы. После правки проверь curl-ом, что секретные файлы отдают 403, а сайт открывается нормально.»*

✅ **Безопасно, если…** запрос секретного файла через браузер возвращает «доступ запрещён» (403), а обычные страницы сайта открываются как прежде.

### Дверь 8. Нет security-заголовков

- **Симптом:** сайт не говорит браузеру, как себя вести безопасно (нет HSTS, X-Frame-Options, X-Content-Type-Options).
- **Фикс:** добавить заголовки в nginx.
> **Промпт:** *«Добавь для `<ТВОЙ_ДОМЕН>` базовые security-заголовки: HSTS, X-Frame-Options (защита от кликджекинга), X-Content-Type-Options: nosniff. После правки проверь заголовки curl-ом и убедись, что сайт открывается без ошибок.»*

✅ **Безопасно, если…** заголовки видны в ответе сервера, а сайт работает.

### Дверь 9. Открытые эндпоинты без проверки (broken authz)

- **Симптом:** есть служебные адреса/API, которые открываются **без логина** — данные видит любой, кто угадал ссылку.
- **Фикс:** закрыть авторизацией.
> **Промпт:** *«Пройди по всем эндпоинтам/страницам, которые отдают личные или служебные данные. Для каждого ответь: можно ли его открыть БЕЗ входа в систему? Где можно — добавь проверку авторизации. Выдай мне таблицу: адрес → нужен ли логин сейчас → нужен ли по-хорошему → что исправил.»*

✅ **Безопасно, если…** ни один адрес с личными/служебными данными не открывается без входа.

## Раздел 3. Закрыть все контуры (личное, изоляция, бот, турникет)

Это самый важный раздел лично для тебя. Технику из Раздела 2 знает любой сисадмин. А вот **не увезти на сервер то, что должно остаться только у тебя** — это про второй мозг, и об этом почти никто не думает.

### 3.1. Личный контур не уезжает на сервер

Когда мы «переезжаем мозгом на сервер», велик соблазн синхронизировать туда **всё**. Но часть мозга — это **личное**: здоровье, семья, финансы, личные переписки, сырые размышления. Серверу они не нужны для работы бота — а риск утечки с сервера всегда выше, чем с твоего личного ноутбука.

Правило простое: **на сервер едет только то, что нужно боту/сайту для работы. Личное остаётся дома.**

Не переносим на сервер:
- папку `personal/` (здоровье, семья, финансы, юридическое);
- папку `sessions/` и любые сырые логи диалогов;
- всё, что помечено как секретное/личное.

> **Промпт агенту (проверка перед синхронизацией):**
> *«Я переношу второй мозг на сервер. Составь список папок, которые поедут. Отдельно выпиши всё, что похоже на ЛИЧНОЕ — папки `personal/`, `sessions/`, сырые диалоги, файлы про здоровье/семью/финансы. Эти папки в синхронизацию НЕ включай и добавь в список исключений. Покажи мне финальный список "едет / остаётся дома" на подтверждение перед первой синхронизацией.»*

✅ **Безопасно, если…** папки `personal/` и `sessions/` физически отсутствуют на сервере, а в правиле синхронизации они прописаны в исключениях (проверяемо: спроси агента «покажи, что этих папок на сервере нет»).

### 🔴 Если мозг уже уезжал на сервер целиком (ветка B): ревизия старой копии

Этот подраздел — **только для ветки B**: если раньше твой второй мозг уже переезжал на сервер **целиком**. Тогда на сервере может лежать **старая полная копия или архив** (папка-дубль, `.tar.gz`, `.zip`, старый бэкап), в котором осталось **личное** — здоровье, семья, переписка, финансы. Оно не нужно серверу для работы, но тихо лежит там и создаёт риск. Мы это найдём и аккуратно уберём.

> Если ты **ветка A** (мозг никогда не уезжал на сервер целиком) — этот подраздел можно спокойно пропустить.

Делаем бережно: сначала — только показать список, потом с твоего «да» перенести личное к тебе на ПК, проверить, что открывается, и лишь в самом конце — удалить старую копию с сервера. Ничего необратимого без подтверждения.

> **Промпт агенту (ревизия старой копии):**
> *«Ты — мой офицер безопасности, работаешь бережно. Раньше мой второй мозг, возможно, уже целиком уезжал на этот сервер, и там могла остаться СТАРАЯ полная копия или архив, где сохранилось ЛИЧНОЕ — здоровье, семья, переписка, финансы. Действуй строго по шагам; ничего необратимого без моего «да»; значения секретов и содержимое личных файлов в чат НЕ выводи — только пути и краткие пометки «что это».*
> *1. НАЙДИ на сервере старые полные копии/архивы мозга и загляни в них на предмет личного: папки вроде `personal/`, `sessions/`, файлы про здоровье/семью/финансы/переписку, а также архивы (`.tar.gz` / `.zip` / `.bak`) со следами этого. Покажи мне СПИСКОМ: путь → что это → почему выглядит личным. Пока НИЧЕГО не трогай.*
> *2. После моего «да» ПЕРЕНЕСИ найденное личное ко мне на локальный ПК по SSH, в папку: Windows — `%USERPROFILE%\Documents\brain-личное\`; macOS/Linux — `~/brain-личное/`. На этом шаге только копируем (с сервера пока не удаляем).*
> *3. ПРОВЕРЬ, что личное реально перенеслось и открывается на ПК: список файлов, размеры, пробно открой пару файлов. Личное должно остаться ТОЛЬКО на ПК.*
> *4. Покажи мне ИТОГ: что перенесено и где лежит на ПК. Дождись моего подтверждения «всё на месте, открывается».*
> *5. Только ПОСЛЕ подтверждения — УДАЛИ старую копию/архив с личным на сервере. Сначала покажи точный список того, что удалишь, я скажу «да».»*

✅ **Безопасно, если…** старой полной копии/архива с личным на сервере больше **нет**; всё личное лежит **только** на твоём ПК (в `brain-личное/`) и открывается; на сервере остался только рабочий контур; и на каждом необратимом шаге (перенос, удаление) агент дождался твоего «да».

### 3.2. Изолированный пользователь для мозга

Мозг/бот должен работать под **отдельным пользователем** с минимальными правами, а его рабочая папка — закрыта правами `700` (только владелец заходит). Тогда даже если что-то в системе пойдёт не так, чужой процесс не прочитает содержимое мозга.

> **Промпт:** *«Проверь, под каким пользователем работает мой бот/мозг. Если под root или под общим пользователем — предложи вынести его в отдельного изолированного пользователя с минимальными правами. Рабочую папку мозга закрой правами 700. Покажи план перед выполнением.»*

✅ **Безопасно, если…** мозг работает не под root, а под отдельным пользователем; его папка имеет права `700`; другой пользователь машины её содержимое прочитать не может.

### 3.2-бис. Поджать права ВНУТРЕННИХ папок мозга

Верхнюю папку мозга мы закрыли (`700`) в шаге выше — снаружи уже не пройти. Но после переезда (особенно **с Windows**, где права на файлы устроены иначе) **внутренние** папки и файлы мозга могут оказаться с избыточно открытыми правами — «читать может кто угодно на машине». Снаружи это не страшно (верхняя дверь заперта), но по-хорошему стоит поджать и внутренние двери — чтобы содержимое видел только владелец.

> **Промпт:** *«Проверь права на ВНУТРЕННИЕ папки и файлы моего мозга под изолированным пользователем. Если внутри есть что-то, доступное на чтение другим (group/other), поджми одной командой — `chmod -R go-rwx` на папку мозга — так, чтобы читать/писать мог только владелец. Сначала покажи, что именно изменится, затем выполни и подтверди, что бот/мозг после этого работают как прежде.»*

✅ **Безопасно, если…** внутренние папки мозга доступны **только владельцу** (для group/other прав на чтение нет), а бот/мозг после правки работают штатно.

### 3.3. «Белый список» бота — бот отвечает только тебе

Если у тебя есть Telegram-бот, подключённый к мозгу, — по умолчанию **написать ему может кто угодно**, кто узнает имя бота. Нельзя, чтобы чужой человек через бота дёргал твой мозг. Ставим whitelist: бот реагирует **только на владельца** (и явно разрешённых людей).

> **Промпт:** *«У моего бота есть доступ к личному мозгу. Добавь "белый список": бот обрабатывает сообщения ТОЛЬКО от разрешённых Telegram ID (мой ID — `<ID_ВЛАДЕЛЬЦА>`). Всем остальным — вежливый отказ, и запиши попытку в лог. Покажи, где список, чтобы я мог добавить людей позже.»*

✅ **Безопасно, если…** сообщение от любого постороннего ID получает отказ и не доходит до мозга, а ты (`<ID_ВЛАДЕЛЬЦА>`) отвечаешь как обычно.

### 3.4. «Турникет», если бот или эндпоинт зовёт модель (защита подписки)

Если твой бот или какой-то адрес на сайте **обращается к ИИ-модели** (по твоей подписке) — это точка, где можно «слить» твою подписку. Представь: кто-то пишет простой скрипт, который дёргает твой адрес 10 000 раз за ночь. Каждый вызов тратит твою подписку. К утру лимит исчерпан, всё встало. Это называют «сливом токенов».

Чтобы этого не случилось, перед публикацией любого адреса, зовущего модель, ставим **турникет из 4 уровней**:

1. **Проверка «свой/чужой» (origin/referer):** запрос принимается только с твоей страницы. Чужой скрипт → отказ.
2. **Проверка формата ввода:** мусор и абракадабра отсекаются **до** обращения к модели.
3. **Не звать модель впустую:** если обрабатывать нечего — модель не вызывается (ноль потраченных токенов).
4. **Ограничение частоты (rate-limit) по IP + счётчик:** один источник не может долбить бесконечно; всплеск запросов → запись и сигнал тебе.

> **Промпт:** *«У меня есть бот/эндпоинт, который вызывает ИИ-модель по моей подписке. Поставь "турникет" из 4 уровней: (1) принимать только запросы с моей страницы (проверка origin/referer); (2) валидировать формат ввода и отсекать мусор ДО вызова модели; (3) если данных для обработки нет — модель не вызывать; (4) ограничение частоты по IP плюс счётчик с сигналом мне при всплеске. Проверь на сценарии: "если запустить скрипт с 10 000 запросов за ночь — исчерпается ли подписка?" Если да — турникет не готов, доработай.»*

✅ **Безопасно, если…** на вопрос «10 000 запросов скриптом за ночь исчерпают подписку?» честный ответ — **нет**: чужой источник отсекается, мусор не доходит до модели, а частота ограничена.

## Раздел 4. Ретро-проверка перед публикацией на GitHub

Рано или поздно ты захочешь показать свой проект миру или просто хранить копию кода на GitHub. GitHub — **публичное** место (а даже приватный репозиторий однажды можно случайно открыть). Поэтому перед тем как что-то туда отправить — проходим **гейт**. Гейт значит: пока не прошёл проверку — не публикуем.

Что не должно уехать на GitHub **никогда**:
- **Секреты и токены** — пароли, ключи API, ключ бота, ключ подписки к модели.
- **Реальный IP-адрес сервера**, реальные домены внутренних сервисов, порты.
- **Личные данные** — здоровье, семья, финансы, чужие имена/контакты/переписки.
- **Сырые диалоги** — необработанные логи чатов, транскрипты, папка `sessions/`.

Вместо всего этого в публичном коде должны быть **плейсхолдеры** — `<ТВОЙ_ДОМЕН>`, `<SSH_ПОРТ>`, `<ТОКЕН>` и т.п.

> **Промпт агенту (гейт перед публикацией):**
> *«Я собираюсь опубликовать этот проект на GitHub. Проведи ретро-проверку как офицер безопасности и дай вердикт 🟢/🔴. Найди и покажи мне ВСЁ, что нельзя публиковать: (1) секреты и токены (в коде, в конфигах, в истории git); (2) реальные IP-адреса, внутренние домены и порты; (3) личные данные — здоровье, семья, финансы, чужие имена и контакты; (4) сырые диалоги, транскрипты, папку sessions. По каждой находке скажи: файл, строка, что именно, и на какой плейсхолдер заменить. Проверь и текущие файлы, и историю git. Пока хоть одна находка красная — вердикт 🔴, публиковать нельзя.»*

> **Промпт (настроить защиту на будущее):**
> *«Чтобы это не повторялось: добавь в `.gitignore` папки `personal/`, `sessions/`, файлы с секретами и `~/.config`-подобные пути. Предложи простой предпубликационный чек (например, поиск по проекту слов, похожих на токены и IP-адреса), который я смогу запускать перед каждой отправкой на GitHub.»*

✅ **Безопасно, если…** вердикт агента — 🟢; в коде и в истории git нет ни одного реального секрета, IP, личного файла или сырого диалога — только плейсхолдеры; `personal/` и `sessions/` в `.gitignore`; и ты можешь честно сказать: «если этот репозиторий завтра станет публичным — мне не будет стыдно и ничего не утечёт».

## Итоговый чек-лист (распечатай и отмечай галочками)

- [ ] Секреты — по стандарту своей ОС (Windows: `%USERPROFILE%\.secrets\` или Credential Manager; macOS/Linux: `~/.config` с правами `600` или Keychain). Не в чате, не в коде, не в git.
- [ ] Файлы секретов на сервере — права `600` (не `644`).
- [ ] SSH-ключ настроен и **проверен во втором окне** до отключения пароля.
- [ ] Вход по паролю и под root — отключён (после проверки ключа).
- [ ] SSH — на нестандартном порту `<SSH_ПОРТ>`.
- [ ] Файрвол ufw включён (SSH-порт разрешён **до** enable), fail2ban работает.
- [ ] Автообновления включены; ребут — только с твоего согласия.
- [ ] Секреты/бэкапы/код не отдаются через браузер (403); стоят security-заголовки.
- [ ] Служебные эндпоинты закрыты авторизацией.
- [ ] `personal/` и `sessions/` — **не на сервере**, в исключениях синхронизации.
- [ ] *(ветка B)* Старая полная копия/архив на сервере проверена: личное перенесено на ПК, старая копия удалена.
- [ ] Мозг работает под изолированным пользователем, папка `700`.
- [ ] Внутренние папки мозга поджаты (`chmod -R go-rwx`) — доступны только владельцу.
- [ ] Бот отвечает только владельцу (whitelist `<ID_ВЛАДЕЛЬЦА>`).
- [ ] Если бот/эндпоинт зовёт модель — стоит турникет (4 уровня), тест на 10 000 запросов пройден.
- [ ] Перед GitHub — гейт 🟢: только плейсхолдеры, ноль реальных секретов/IP/личного.
