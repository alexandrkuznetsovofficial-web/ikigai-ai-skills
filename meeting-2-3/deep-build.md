# Deep Build — методология глубокой разработки

> Не кодируй ради кода. Перед каждым изменением спроси:
> это реально решает задачу? Это самое эффективное решение?

---

## Шаг 0 — Интеграция с твоим проектом (всегда первым)

Перед тем как начать — прочитай контекст проекта:

1. Проверь есть ли `CLAUDE.md` в корне. Если есть — прочитай целиком.
2. Проверь есть ли `plans/` — там история прошлых планов.
3. Проверь есть ли `brain/`, `second-brain/`, `ai-clone/`, `business/` — папки Second Brain.
4. Если нашёл — работай с ними, не создавай дублей.
5. Создай нужные папки если их нет:
   ```
   mkdir -p plans plans/archive
   ```
6. Проверь есть ли `.git` в папке проекта. Если нет — git не используем, этапы с ветками пропускаем.
7. Если в `CLAUDE.md` нет блока про deep-build — предложи добавить:
   ```
   ## Разработка
   Для нетривиальных задач — /deep-build (методология глубокой разработки).
   ```

Только после этого — к задаче.

## Выбери режим по размеру задачи

| Задача | Размер | Этапы |
|--------|--------|-------|
| Багфикс, правка 1–2 файлов | **S** | 1 → 4 → 5 → 6 → 7 → коммит |
| Новая фича, модуль, 3–10 файлов | **M** | Этапы 1–10 |
| Новый сервис, изменение архитектуры | **L** | Все 12 этапов |

Правило: не знаешь размер — спроси пользователя одним вопросом.

---

## Этапы

### Этап 1 — Исследование (Read-Only, никакого кода)

- Изучи структуру проекта, зависимости, паттерны, тесты (если есть)
- Поищи: кто уже решал эту задачу? Какое самое эффективное известное решение?
- Не изобретай велосипед — найди лучший существующий подход
- Завершение: `plans/YYYY-MM-DD-<задача>-research.md`

→ `/compact` если контекст заполнен больше 40%

---

### Этап 2 — Спецификация (только для M и L)

**Спек = ЧТО и ЗАЧЕМ. Не КАК. Спек — это контракт.**

Зафикси:
- Проблема (одно предложение)
- Цель (один измеримый результат)
- Что входит в скоуп / что нет
- Критерии приёмки (как поймём что готово?)

Сохранить: `plans/YYYY-MM-DD-<задача>-spec.md`

---

### Этап 3 — План + Самопроверка

Построй план по фазам. После — обязательная проверка по трём вопросам:

```
1. ЭТО РЕАЛЬНО РЕШАЕТ ЗАДАЧУ?
   Сравни каждый пункт плана с критериями приёмки из спека.
   Если хоть один критерий не закрыт — план неполный.

2. ЭТО САМОЕ ЭФФЕКТИВНОЕ РЕШЕНИЕ?
   Назови 2-3 альтернативных подхода с плюсами и минусами.
   Обоснуй почему выбранный лучше.

3. ЕСТЬ ЛИ «КОД РАДИ КОДА»?
   Каждое изменение должно прямо решать задачу.
   Если изменение не связано с задачей — убери из плана.
```

Сохранить: `plans/YYYY-MM-DD-<задача>-plan.md`

---

### Этап 4 — Реализация по фазам

**Каждая фаза = отдельная задача с чистым фокусом.**

Порядок внутри каждой фазы:
1. Если есть git → переключись на ветку `feature/<задача>`
2. Если есть тесты в проекте → сначала напиши тест (он должен упасть — это норма), потом код
3. Если тестов нет → пиши код напрямую, проверяй вручную
4. После кода → Self-Audit (Этап 5)
5. Верификация (Этап 6)
6. Impact (Этап 7)
7. Коммит

**Правило старта:** начинай реализацию только после слов «Приступай» или «Реализуй Фазу N». До этого — только план.

→ `/compact` после каждой фазы если контекст > 40%

---

### Этап 5 — Self-Audit (после каждой фазы)

```
Проверь реализацию фазы:

1. СООТВЕТСТВИЕ КРИТЕРИЯМ
   Для режима M/L: открой spec, пройди каждый критерий приёмки.
   Для режима S: проверь что изменение решает именно то что просили.
   Если критерий не закрыт — доделай.

2. КРИТИКА РЕШЕНИЯ
   Посмотри на код свежим взглядом.
   Это реально решает задачу?
   Есть более простой или эффективный способ?
   Есть изменения не связанные с задачей — убери.
```

---

### Этап 6 — Верификация (поиск реальных багов)

**Не «причёсывание». Ищем только доказуемые баги.**

Шаг 1 — Найти:
```
Проверь код фазы:
- Логические ошибки (неверные условия, edge cases)
- Обработка данных (None/null, типы, граничные значения)
- Безопасность (открытые секреты в коде, небезопасные запросы)
- Производительность (очевидные узкие места)
```

Шаг 2 — Верифицировать:
```
Для КАЖДОГО найденного бага:
- Это реальный баг или false positive?
- Можешь показать где конкретно это сломается?
- Если нет — НЕ баг. Не трогай.

Правило: не чини код «для красоты». Только доказанные баги.
```

---

### Этап 7 — Impact (что сломалось в других частях?)

```
Обязательная проверка перед коммитом:

1. РЕГРЕССИЯ
   Какие файлы/модули зависят от изменённых?
   Если есть тесты — запусти все, не только для текущей фазы.
   Если тестов нет — пройди зависимые места глазами.
   Если что-то сломалось — это приоритет №1.

2. ПОБОЧНЫЕ ЭФФЕКТЫ
   Изменились ли интерфейсы (API, функции, типы данных)?
   Если да — кто их использует? Все места обновлены?

3. МЫШЛЕНИЕ ВПЕРЁД
   Что может сломаться при неожиданных данных?
   При одновременных запросах (если веб)?
```

---

### Этап 8 — Интеграционная проверка

Все фазы завершены. Проверяем проект целиком:
- Каждый критерий из спека → реализован?
- Попроси Claude пройтись по всем изменённым файлам и проверить связность
- Запусти проект и проверь вручную основной сценарий использования

---

### Этап 9 — Code Review (новая сессия, без предвзятости)

Открой новый чат. Свежий контекст — без истории реализации. Задача: найти то что пропустил.

Чеклист: граничные случаи / одновременные операции / обратная совместимость / безопасность / производительность / обработка ошибок.

Если найдены критичные правки — возврат к Этапу 6.

---

### Этап 10 — Security Check (для M и L)

Попроси Claude проверить код на:
- Секреты и токены захардкоженные в коде
- Небезопасные операции с файлами или внешними данными
- SQL/команды собранные из пользовательского ввода

Это не нужно делать специальными инструментами — Claude сам может пройти код и найти проблемы.

---

### Этап 11 — Фиксы и повторная проверка

Если review/check нашли проблемы:
1. Исправь (только доказанные баги — правило Этапа 6)
2. Повтори Impact Analysis — фиксы ничего не сломали?
3. Повтори review если изменения значительные

---

### Этап 12 — Финал

- Архивировать план: `mv plans/<файл> plans/archive/`
- Спек оставить как документацию
- Если есть git: смержи ветку в main (через PR или напрямую — как удобно)
- **Деплой — только по явному разрешению пользователя**

---

## Правило контекста (40%)

Качество деградирует когда контекст заполнен больше 40-50%.

- `/compact` когда видишь что контекст заполнен — не жди автоматического
- Если совсем перегружен: сохрани прогресс → `/clear` → начни новую сессию с handoff-файлом

Перед `/clear` всегда создай `plans/<задача>-handoff.md`:
```
## Handoff
Задача: [что делаем]
Завершено: [фазы/этапы]
Следующий шаг: [с чего продолжить]
Ключевые решения: [почему так]
```

---

## Модели по этапам

| Этап | Модель | Почему |
|------|--------|--------|
| Исследование, планирование (1–3) | Opus | Лучше в кросс-файловом анализе и планировании |
| Реализация (4–7) | Sonnet | Быстрее, экономичнее на рутинном коде |
| Code Review, Security (9–10) | Opus | Глубокий анализ, ловит неочевидные баги |

Если задача небольшая — можно работать на Sonnet весь цикл.
