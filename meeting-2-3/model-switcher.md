# MODEL SWITCHER — автоматический подбор модели под задачу

> Не все задачи одинаковые. Правильная модель = лучше результат + меньше расхода подписки.

---

## ⚙️ УСТАНОВКА (Claude выполняет это ОДИН раз, сразу при загрузке скилла)

Когда пользователь просит установить этот скилл — сделай два шага:

**Шаг 1.** Определи корень проекта: это папка, которую пользователь открыл в VS Code
(рабочая директория Claude Code). Сохрани этот файл в
`<корень проекта>/.claude/skills/model-switcher/SKILL.md` (если папок нет — создай).

**Шаг 2.** Допиши в конец файла `CLAUDE.md` в этом же корне проекта — именно в том,
где уже лежит CLAUDE.md пользователя, если он есть; второй CLAUDE.md не создавай —
блок:

```markdown
## ПРАВИЛО: Model Switcher (автопроверка модели)

При старте КАЖДОЙ новой задачи — до начала работы — классифицируй её по
`.claude/skills/model-switcher/SKILL.md` и сравни с текущей моделью.
Если текущая модель НЕ оптимальна — первой строкой ответа выведи:

`🎯 Эта задача — [тип]. Переключись: /model [название] — [почему, одна фраза].`

Если модель уже оптимальна — ничего не выводи, просто работай.
Не повторяй рекомендацию внутри одной задачи больше одного раза.
```

После установки скажи пользователю: «Свичер установлен. Теперь я сам проверяю каждую
твою задачу и предлагаю переключение одной командой. Само переключение — за тобой:
скопируй команду `/model …`, которую я выведу первой строкой».

---

## Как это работает после установки

1. Ты просто пишешь задачу — как обычно, ничего не вызывая
2. Система **сама** классифицирует её и сверяет с текущей моделью
3. Если модель не оптимальна — первой строкой получаешь готовую команду `/model …` + причину
4. Одно действие: отправляешь эту команду — и работаешь на правильной модели

**Честно про механику:** сменить модель может только пользователь (это защита твоей
подписки — ИИ не может сам тратить твои токены на дорогой модели). Поэтому «автомат» =
автопроверка на каждой задаче + переключение в одно касание.

## Карта моделей

### Haiku — `/model haiku`
**Самая быстрая и дешёвая.**
Быстрый вопрос, перевод, короткое резюме, заголовки, простая классификация.
Не подходит: сложный код, архитектура, многошаговые задачи.

### Sonnet — `/model sonnet`
**Рабочая лошадка — ~80% задач.**
Написать/исправить/объяснить код, рефакторинг, отладка, файлы и компоненты,
тексты среднего объёма, анализ данных, задачи «сделай X».

### Opus — `/model opus`
**Глубокий аналитик — где важно думать, а не просто делать.**
Архитектура, ревью с критическим взглядом, выбор между альтернативами,
стратегические вопросы бизнеса, неочевидные риски, длинные сложные промпты.

### opusplan — `/model opusplan`
**Гибрид: планирует как Opus, выполняет как Sonnet.**
Единственный встроенный авторежим Claude Code. Лучший выбор для сложных задач
с нуля: «помоги понять как сделать X, а потом сделай».

### Fable — `/model fable`
**Максимум. Для самых сложных и долгих задач.**
Автономная работа часами, глубокий ресёрч, хардкорный debugging,
«разберись сам и сделай». Дороже всего — только когда реально нужен максимум.

## Сигналы в тексте задачи → модель

**→ haiku:** «объясни», «что такое», «переведи», «коротко», «резюмируй»
**→ sonnet:** «напиши код», «исправь», «добавь», «сделай функцию», «что не так»
**→ opus:** «как лучше», «какую архитектуру», «сравни подходы», «ревью», «дилемма», «посоветуй»
**→ opusplan:** «спланируй и реализуй», длинная задача с этапами
**→ fable:** «займёт долго», «автономно», «разберись сам», «большой проект», «глубокий анализ»

Если сигналы конфликтуют (например «сравни подходы» + «займёт полдня») — выбирай
более мощную модель из двух: лучше переплатить токенами, чем получить слабый результат.

---

## Бонус: глубина без смены модели — `/effort`

| Команда | Когда |
|---------|-------|
| `/effort low` | Быстрый черновик, скорость важнее |
| `/effort high` | По умолчанию |
| `/effort xhigh` | Сложная задача, больше рассуждений |
| `/effort max` | Только для самых трудных случаев |

Если уже на Sonnet и ответ поверхностный — сначала `/effort xhigh`, потом уже Opus.
