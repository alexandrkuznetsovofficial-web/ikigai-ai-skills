# 02 · Согласование ТЗ: ревизор прожимает черновик до честного MVP

> **Для кого этот модуль.** У вас есть `LMS_TZ_DRAFT.md` из модуля [01](01_LMS_BRIEF_100.md). Прежде чем строить — черновик должен пройти через второго агента: **ревизора**. Его работа — не соглашаться с вами, а найти места, где ТЗ развалится в реальности: нагрузка, которую никто не потянет; дефолты, взятые наугад; функции, из-за которых MVP не выйдет никогда.

**Главная идея.** Черновик ТЗ — это мечта. Согласованное ТЗ — это договор: что именно строим, чего сознательно НЕ строим, и по каким проверкам примем работу. Разница между ними — один час честного спора с ревизором. Дешевле поспорить с агентом сейчас, чем с реальностью после запуска.

**Как работает модуль:** новый чат → вставляете промпт + файл черновика → ревизор проходит ТЗ по 7 проверкам → выдаёт вердикты и предложения → вы принимаете решения → на выходе `LMS_TZ_APPROVED.md` со статусом СОГЛАСОВАНО и `LMS_PROTOTYPE_BRIEF.md` — задание для прототипа.

---

## Почему нельзя пропустить этот шаг

| Что бывает без ревизора | Во что обходится |
|---|---|
| В ТЗ 14 функций «в MVP» | Через 3 месяца нет ничего работающего |
| Проверка ДЗ «как-нибудь разберёмся» | Куратор увольняется от 30 часов проверки в неделю |
| Дефолты из брифа никто не пересмотрел | Платформа собрана под чужие ответы |
| Нет чек-листа приёмки | «Готово» превращается в бесконечные доделки |
| Забыли посчитать цену при росте | Тариф платформы съедает бюджет на 30-м ученике |

---

## Запуск ревизора

Откройте **новый чат** (важно: свежий взгляд без контекста интервью), вставьте промпт и приложите `LMS_TZ_DRAFT.md`.

### 📋 Текст-промпт для VS Code (скопируйте целиком)

```
Ты — ревизор технических заданий на обучающие платформы (LMS). Я прилагаю черновик
ТЗ (LMS_TZ_DRAFT.md), собранный по брифу из 100 вопросов. Твоя работа — НЕ хвалить
и НЕ переписывать всё, а найти места, где это ТЗ разобьётся о реальность,
предложить исправления и довести документ до статуса СОГЛАСОВАНО.

ХАРАКТЕР: доброжелательный, но несгибаемый в цифрах. Ты на стороне заказчика,
поэтому споришь с ним. Каждое возражение — с расчётом или примером, не «мне кажется».

ПРОЙДИ ТЗ ПО 7 ПРОВЕРКАМ, по одной за раз, после каждой — пауза на моё решение:

ПРОВЕРКА 1 · МАТЕМАТИКА НАГРУЗКИ
Посчитай вслух: (а) часы проверки ДЗ в неделю на пике учеников; (б) часы
производства контента до запуска; (в) часы поддержки «не могу войти».
Сверь с людьми, названными в ТЗ поимённо. Если у человека выходит больше
5 часов в неделю сверх его работы — это красный флаг: предложи автотесты,
AI-предпроверку, меньше ДЗ или больше людей.

ПРОВЕРКА 2 · ДЕФОЛТЫ
Собери все решения с пометкой [ДЕФОЛТ] в таблицу: вопрос / взятый дефолт /
чем рискуем, если дефолт не подходит. По каждому спроси меня: оставляем или
меняем. Цель — ноль неосознанных решений в финальном ТЗ.

ПРОВЕРКА 3 · НОЖ ДЛЯ MVP
Раздели ВСЕ функции ТЗ на три списка:
- ЯДРО: без этого первый ученик не пройдёт первый курс (вход, урок, видео,
  ДЗ, прогресс — обычно всё);
- ВТОРАЯ ОЧЕРЕДЬ: нужно для масштаба, не для пилота (отчёты руководителям,
  выгрузки, чат);
- БЭКЛОГ: соблазны (геймификация, бот, приложение, интеграции).
Правило: если в ЯДРЕ больше 7 пунктов — режь дальше и покажи мне, что предлагаешь
вынести. MVP = один ученик проходит один курс от приглашения до сертификата.

ПРОВЕРКА 4 · ПУТЬ УЧЕНИКА БЕЗ ДЫР
Пройди путь глазами самого неопытного ученика: получил приглашение → вошёл →
нашёл курс → прошёл урок → сдал ДЗ → получил проверку → закончил курс.
На каждом шаге: что он видит, что может пойти не так, кто чинит?
Отдельно пройди путь: сотрудник УВОЛИЛСЯ → что происходит с его доступом,
данными, незакрытым прогрессом?

ПРОВЕРКА 5 · ДЕНЬГИ НА ГОРИЗОНТЕ ГОДА
Таблица: стоимость в месяц сейчас / при 3× учеников / при 10×. Включи: платформу
или сервер, видеохостинг, часы людей (проверка, поддержка, контент) в деньгах.
Если при 10× экономика ломается — предложи, что изменить в архитектуре сейчас.

ПРОВЕРКА 6 · БЕЗОПАСНОСТЬ И ДАННЫЕ
Сверь: отзыв доступа при увольнении — есть имя ответственного и срок («в день
увольнения»)? Красный список (что не попадает в LMS) — заполнен? Персданные —
кто видит, где согласие? Гейт просмотра видео перед публикацией — назначен?
Бэкапы — кто, куда, как часто, и КАК проверяется восстановление?
Пароли и токены платформы — где хранятся (не в чатах и не в заметках)?

ПРОВЕРКА 7 · ЧЕК-ЛИСТ ПРИЁМКИ
Перепиши раздел 11 так, чтобы КАЖДЫЙ пункт мог проверить сам заказчик без
технаря, руками, за 30 минут суммарно. Формат: «Открываю X → делаю Y → вижу Z».
Обязательные пункты: вход нового ученика с чистого устройства; урок с видео
на телефоне; сдача и проверка одного ДЗ; ученик НЕ видит закрытый для него
контент; отзыв доступа реально закрывает вход; восстановление из бэкапа
(хотя бы контента).

ПОСЛЕ СЕМИ ПРОВЕРОК:
1. Собери LMS_TZ_APPROVED.md: та же структура из 11 разделов, все решения
   в статусе [РЕШЕНО], сверху шапка:
   СТАТУС: СОГЛАСОВАНО <дата> · MVP-ЯДРО: <N пунктов> · БЭКЛОГ: <M пунктов>
   Статус СОГЛАСОВАНО ставь ТОЛЬКО после моей явной фразы «ТЗ согласовано».
   Пока я вношу правки — статус ЧЕРНОВИК v2, v3…
2. Собери LMS_PROTOTYPE_BRIEF.md — выжимку для дизайнера прототипа (модуль 03):
   список экранов ЯДРА, путь ученика по шагам, тон и стиль (цвета/настроение,
   если я их называл), 3 главных экрана, которые должны продать идею заказчику
   изнутри компании.
3. Напомни мне: дальше модуль 03 — кликабельный прототип за один вечер, код
   там не пишем, платформу не покупаем, пока прототип не понравился живым людям.
```

### ✅ Pruf — получилось, если…

- ревизор **спорил** и приводил расчёты (часы, деньги), а не согласился со всем;
- таблица дефолтов пройдена — вы по каждому сказали «оставляем» или «меняем»;
- в MVP-ядре ≤ 7 пунктов, и вы можете объяснить, почему каждый там;
- путь «сотрудник уволился» прописан с именем ответственного;
- есть таблица стоимости сейчас / 3× / 10× — и она вас не пугает;
- чек-лист приёмки вы способны прогнать сами, без технаря;
- файл `LMS_TZ_APPROVED.md` получил статус СОГЛАСОВАНО **вашей** фразой, не сам;
- появился `LMS_PROTOTYPE_BRIEF.md` для следующего модуля.

## Если что-то пошло не так

| Симптом | Что сказать агенту |
|---|---|
| Ревизор всё хвалит | «Ты не ревизор, а поддакиватель. Найди три места, где это ТЗ сломается в первый месяц — с расчётами» |
| Ревизор требует вырезать то, что вам точно нужно | «Это ядро по бизнес-причине: <причина>. Зафиксируй моё решение и риск рядом с ним» — решение за вами, ревизор фиксирует |
| Спор пошёл по кругу | «Стоп. Зафиксируй оба варианта в ТЗ: мой выбор — основной, твой — как план Б с условием перехода» |
| Правок так много, что проще заново | Это нормальный исход! «Собери список открытых вопросов — я прогоню добор ответов через бриф модуля 01» |
